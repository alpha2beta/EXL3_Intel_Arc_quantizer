# Arc 140V Adaptation Guide for the EXL3 Quantizer

**Target:** User-confirmed Intel Core Ultra 7 258V with 32 GB system memory and Intel Arc 140V integrated graphics.  
**Date:** October 20, 2026.  
**Applies to:** `EXL3_Intel_Arc_quantizer.md` version 3.2 and its derived `tasks.md`.  
**Document role:** Proposed specification/documentation amendments. This guide does not itself modify those files or establish a working quantizer port.

## 1. Decision and evidence boundary

Make the 140V/258V machine the **primary prototype platform**, rather than requiring an A770/B580 before development starts. Keep discrete Arc qualification as a separate optional deployment track. This is an engineering recommendation, not a measured performance or full-model capacity claim.

PyTorch's hardware documentation includes Lunar Lake, and its published PyTorch 2.7 results explicitly include the Ultra 7 258V with Arc 140V. This supports selecting the platform for XPU development; it does not prove that the custom EXL3 encoder, required factorization dtypes, or complete conversion pipeline work unchanged. [R1][R2]

The 258V combines Arc 140V with 32 GB of on-package memory. The integrated GPU uses system memory rather than a separate discrete-card VRAM pool. Do not describe this machine as having “32 GB VRAM,” or add a GPU-reported memory budget to 32 GB as if they were independent physical capacities. [R3][R4]

**Unchanged project objective:** generate compatible EXL3 checkpoints while preserving the pinned upstream quantization algorithm. The inference runtime remains a validation tool, not the implementation deliverable. [D1]

## 4. Memory model: one physical pool, multiple accounting views

### 4.1 Keep scratch arithmetic unchanged

Changing from discrete Arc to 140V does not by itself change the upstream scratch shapes. Re-audit them at the pinned commit, then retain these sizing fixtures from the assessment. They describe storage, not all native arithmetic or total process memory. [D1]

```text
S = 65536 >> K
T = 256
B = chosen scratch batch capacity

cost_bytes = B * 2 * S * 2
edge_bytes = B * T * S * 2
```

For K=2, the calculated edge/cost allocations are:

| B | Edge storage | Cost storage |
| ---: | ---: | ---: |
| 1 | 8 MiB | 64 KiB |
| 16 | 128 MiB | 1 MiB |
| 64 | 512 MiB | 4 MiB |
| 128 | 1 GiB | 8 MiB |
| 256 | 2 GiB | 16 MiB |

These are arithmetic examples, not recommended maximum batches or measured 140V allocations. Other K values require their own calculation.

### 4.2 Replace the capacity policy

**Proposed admission checks:**

1. Each requested allocation fits the validated single-allocation limit.
2. The runtime accepts the aggregate device allocation plan.
3. The system retains the configured available-memory reserve after other live allocations.
4. The workload avoids sustained paging/pressure and remains responsive under the chosen operating conditions.

Use separate views:

- Framework live and reserved XPU allocations.
- Runtime-reported free/total GPU memory and allocation limits.
- OS total/available memory, process RSS/PSS where available, swap activity, and memory-pressure indicators.
- Stage-level allocation lifetimes and observed peaks.

PyTorch documents `torch.xpu.memory.mem_get_info()` as a free/total device-memory query. Treat its values as one runtime view, not a guarantee that all reported free bytes are safely allocatable by the quantizer. Verify API availability and behavior in the pinned release. [R5]

**Avoid double counting:** CPU RSS, GPU allocations, shared mappings, and driver accounting can overlap. Do not simply sum every reported number. Use OS physical-memory pressure as an independent guardrail, and document which allocations are distinct copies versus shared backing. This is a proposed measurement policy.

### 4.3 Initial tuning policy

- Begin with B=1 or another small validated batch; increase only after correctness and memory instrumentation work.
- Compare feasible batches such as 16, 64, 128, and 256; retain the best measured operating point, not the largest allocation.
- Make the system-memory reserve configurable. A preliminary 6–8 GiB reserve may be used as a conservative experiment setting, but it is not a hardware requirement or a guarantee of safety.
- Keep cached scratch bounded; include CPU fallback workspaces, fixture loading, prefetch, and serialization in the live-allocation plan.
- Stop or reduce the workload when the reserve is breached or sustained paging appears. Do not count swap as additional GPU capacity.
- Do not alter tile length, tail closure, or error-feedback order to force a fit without a separate algorithmic validation.

All values in this tuning policy are proposed experiment settings, not measured results.

## 5. Traceback and CPU fallback on an integrated GPU

Keep the three comparison candidates: GPU-resident traceback, explicit transfer plus CPU traceback, and host-accessible predecessor storage. [D1]

Change the benchmark labels from “PCIe transfer cost” to **data-movement, synchronization, placement, and shared-memory contention cost** for the 140V profile. Shared physical memory does not prove that framework CPU and XPU tensors alias the same storage, that transfers disappear, or that arbitrary host pointers are device-accessible.

**Proposed experiments:**

- Verify the actual USM/allocation capabilities and supported framework integration.
- Check whether a path creates a second copy, stages data, migrates pages, or synchronizes execution.
- Compare complete search-plus-traceback latency and system-memory pressure, not just copy-call duration.
- Compare CPU traceback thread counts and sequential versus overlapped execution; do not assume CPU/GPU overlap is faster.
- Measure factorization fallback with its own host allocations and synchronization.
- Prefer GPU-resident traceback as a correctness baseline, not as a predetermined winner.

No zero-copy or overlap speedup is asserted here.

## 6. Environment and kernel qualification

Retain Linux as the initial project policy, not as a claim that other OS modes cannot run XPU. PyTorch lists supported Windows, Linux, and WSL configurations; the exact project environment must still be pinned and tested. [R1]

**Add to the compatibility manifest:**

```text
profile: lunar_lake_140v_258v_32gb
cpu: Intel Core Ultra 7 258V
memory_configuration: 32 GB shared system memory
memory_model: integrated GPU / shared physical pool
os_mode: native Linux / WSL / Windows (record actual selection)
gpu_identity: queried name, device ID, driver and runtime
software_stack: exact versions and build provenance
allocation_limits: queried and experimentally validated
supported_subgroups_and_local_memory: queried, not assumed
power_profile_and_ac_state: recorded for each benchmark
initial_model_codebook_K: explicitly selected
system_memory_reserve: configurable, record units
qualification_status: untested / tile / layer / full-model
```

This is a proposed manifest schema, not a ready-to-run configuration for an existing converter.

Do not copy B580 launch geometry, GRF settings, local-memory assumptions, or AOT device identifiers into the 140V profile without compiler/runtime verification. Test the custom extension, required dtypes, stream/queue integration, allocation limits, and generated kernel resource use on the actual device. [D1]

Record AC/battery state, cooling/power mode, sustained clocks or available telemetry, background load, and thermal behavior. These are proposed benchmark controls; do not forecast conversion time from nominal bandwidth, GPU branding, or NPU TOPS.

## 8. Revised exit gates

**Gate 0: platform readiness.** Pinned native source and environment, trusted fixtures, working extension, measured capabilities, and memory instrumentation. PyTorch platform support alone does not pass this gate.

**Gate 1: tile encoder.** Correct selected encoder configuration, bounded scratch, tested failure handling, and measured throughput/traceback choice on 140V.

**Gate 2: complete single layer.** Applicable acceptance tiers 1–4 pass; all live CPU/XPU allocations fit the validated operating envelope without sustained paging or hidden algorithm changes.

**Gate 3: bounded full model.** The selected model passes quality and interoperability tiers 5–6, recovery tests, and measured memory/reliability criteria on 140V. If not, report tile/layer prototype status rather than full-model support.

**Optional discrete gate.** Independently qualify a named discrete Arc device with its own memory model and benchmark results. This is not required to claim a narrowly scoped 140V-only implementation.

These gates adapt the original plan; they do not relax numerical or checkpoint-compatibility requirements. [D1][D2]
