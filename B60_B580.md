## 1. Why this plan exists

The declared Active Target (`empero-ai/Qwen3.8-9B-Distill`, hybrid qwen3_5 text tower) was converted
on the Arc 140V **integrated** GPU. That host turned out to be memory-starved for this workload: the
device pool is carved out of the same 30.9 GiB of system RAM as the host, so the page cache, `zram`
and the desktop's own GPU allocations squeeze the pool the converter needs. Eight attempts were
needed; three genuine defects were found and fixed on the way (see §7).

A discrete board changes the memory model completely (dedicated VRAM, no UMA contention) and roughly
doubles the encoder throughput. **This plan is the qualification of that claim — it must be measured,
not assumed.**

### Baseline to beat (measured on the 140V host, `progress.md` Step 25/26)

| Metric | Value |
|---|---|
| Tile encoder throughput | **724 tiles/s** (K=2, global-cost mode) = **1.6 ms/tile** incl. transfers |
| Encoder work | 33,554,432 branch-metric transitions per tile; SLM (66.4 KiB) caps occupancy to 1 WG/Xe-core |
| Layer time (6 quantized modules, real GSS) | **~28 min** (1628–1712 s measured, 10 layers) |
| Full 32-layer run | ~15 h wall clock, ~894 min extrapolated |
| Device working set (steady state) | ~2.0–2.5 GiB live XPU allocation (hidden states 2.1 GiB + Hessians ~1.5 GiB) |
| Host RSS | 1.6–3.4 GiB (streamed, one layer resident) |
| Output bundle | 6.73 GiB (1.64 GiB layer artifacts + 5.09 GiB bit-exact pass-through) |
| Effective bpw | 5.99 bpw whole checkpoint / 2.05 bpw over the quantized text-tower linears (K=2) |

### Expected outcome (estimate — to be replaced by measurements)

| | Arc 140V iGPU | Arc B580 | Arc Pro B60 |
|---|---|---|---|
| Xe cores vs 140V | 1× | ~2× | ~2.5× |
| Encoder throughput (est.) | 724 tiles/s | ~1.4–1.6 k tiles/s | ~1.8–2 k tiles/s |
| Layer time (est.) | 28 min | **11–15 min** | **8–11 min** |
| Full 32-layer run (est.) | ~15 h | **~6–8 h** | **~4.5–6 h** |

The encoder is **core-count bound** (SLM-limited occupancy, not bandwidth), so discrete scaling should
be close to linear. Two things will *not* speed up and may become the new bottleneck: the CPU-side
`torch.linalg.cholesky` fallback (`exl3_quant/ldlq.py:98`) and the host-side calibration/artifact work.

## 3. Phase A — Environment and device inventory (P3-15, ~1 h)

Record, per board, into `reports/discrete_inventory.md`:

```bash
lspci -nn | grep -iE "vga|display|3d"      # PCI ids, driver binding
xpu-smi dump                                # device name, driver, memory total/used, clock, power
uname -a; cat /etc/os-release
python -c "import torch; print(torch.__version__, torch.xpu.is_available())"
python -c "import transformers; print(transformers.__version__)"
glxinfo -B 2>/dev/null | head -20           # OpenGL renderer string (if present)
for z in /sys/class/thermal/thermal_zone*/temp; do echo "$z $(cat $z)"; done
ipmitool sensor 2>/dev/null | head -30      # server BMC: intake/exhaust temp, fans, power
```

Also capture:

- **PCIe link state and health**: `lspci -vvv -s <bdf>` (link status, max speed/width, error counters
  `DevSta`, `UESta`, `CESta`), and `dmesg | grep -iE "pcie|aer|link down"` for the *pre-existing* error
  counter baseline. The pinned runtime's own log records **"B70 PCIe links are unstable (root cause of
  the crashes)"** with 5 link-down events in 7 days on one machine — **take the baseline before the run**
  so a later link-down can be attributed.
- **Memory semantics** (the decisive difference from UMA):
  ```bash
  python - <<'PY'
  from exl3_quant.memory_policy import capture_snapshot
  s = capture_snapshot(0)
  print("dev_free", s.device_free_bytes/2**30, "GiB  dev_total", s.device_total_bytes/2**30,
        "GiB  sys_avail", s.system_available_bytes/2**30, "GiB")
  PY
  ```
  On the 140V the pool is shared with the host; on a discrete board `dev_free` must be *independent* of
  the host's page cache and `MemAvailable`. **Verify** it by allocating 4 GiB on the XPU and re-reading
  the counters: on the 140V `dev_free` did not move (pool slack), while under pressure it fell.
- **Counter regime** (decides the admission policy — see §7): with a dedicated pool the counters
  normally *do* reflect the live XPU allocation, i.e. the `EXL3_MEMORY_REFLECT_OUTSTANDING=1` regime.
  Determine it empirically before choosing the reserve.

**Gate A:** inventory written, both boards enumerated, PCIe error counters baselined.

## 4. Phase B — Probe the pinned stack (P3-15, ~2 h)

### B1. Tile-encoder throughput (the number that matters)

```bash
python -m unittest discover -s tests -p "test_xpu_quantizer.py" -v   # 13 tests: bit-exact vs the reference encoder
python bench/../scripts/measure_encoder.py --device 0 --tiles 65536   # tiles/s, ms/tile
```

If `scripts/measure_encoder.py` does not exist yet, use the pinned micro-profile that produced the
140V number (65,536 tiles in 107.06 s):

```python
import time, torch
from exl3_quant.ldlq import make_xpu_tile_encoder
enc = make_xpu_tile_encoder(K=2)
tiles = torch.randn(65536, 256, device="xpu:0") * 0.02
enc(tiles); torch.xpu.synchronize(0)          # warm-up
t0 = time.time(); enc(tiles); torch.xpu.synchronize(0)
dt = time.time() - t0
print(f"{65536/dt:,.0f} tiles/s  ({1e3*dt/65536:.3f} ms/tile)")
```

**Run on: B580, Pro B60, and (if the 140V host is reachable) the 140V** for a same-session comparison.

### B2. Memory-policy behaviour (the P3-09 lesson must not repeat blindly)

Sweep the admission knobs and record the usable budget:

```bash
for reserve in 0.5 1 2 4 6; do
  for reflect in 0 1; do
    EXL3_MEMORY_RESERVE_GIB=$reserve EXL3_MEMORY_REFLECT_OUTSTANDING=$reflect \
      python - <<'PY'
    import torch
    from exl3_quant.memory_policy import MemoryPolicy, capture_snapshot
    s = capture_snapshot(0)
    p = MemoryPolicy()
    print(f"reserve={p.reserve_bytes/2**30} GiB reflect={p.reflect_outstanding} "
          f"binding={s.binding_available_bytes/2**30:.2f} GiB "
          f"usable={p.usable_bytes(s, outstanding_bytes=0)/2**30:.2f} GiB")
    PY
  done
done
```

Decision rule for the discrete run: **use the default 6 GiB reserve and the default (unreflected)
counter regime if the sweep shows the pool is comfortably larger than the run's working set**
(~4.6 GiB). Only deviate with a recorded measurement — the 140V run needed two documented deviations
(`EXL3_MEMORY_RESERVE_GIB`, `EXL3_MEMORY_REFLECT_OUTSTANDING=1`) purely because UMA made the pool
starve; that reasoning must **not** be copied blindly.

### B3. Scratch stress and allocation limits

```bash
python -m unittest discover -s tests -p "test_scratch.py" -v
python -m unittest discover -s tests -p "test_memory_policy.py" -v
python -m unittest discover -s tests -p "test_xpu_extension.py" -v
```

Capture the maximum admissible batch `B` per K (the arena adapts it to the live budget) and the
single-allocation ceiling (`max_single_alloc_bytes`) reported by the driver.

**Gate B:** encoder tiles/s per board, the memory-policy table, the scratch limits — recorded in
`reports/discrete_probe.md`.

`checkpoint_interval=1`, corpus = the **wikitext-2-raw-v1 test split** (128×2048, seed-42 offset 3,

```bash
PYTHONPATH=. <venv>/bin/python scripts/run_p3_09.py \
    --model-dir  /path/to/qwen38 \
    --output-dir /path/to/qwen38_exl3_k2_<board> \
    --corpus     /path/to/calibration_tokens_wikitext2_test.json \
    --evidence   /path/to/evidence_<board>
```

Requirements for the driver script (it must exist in the repo — see §8):

- `EXL3_MEMORY_RESERVE_GIB` / `EXL3_MEMORY_REFLECT_OUTSTANDING` set only if Phase B justified them,
- **no cache watchdog on a discrete board** (the 140V watchdog existed only to protect the shared pool),
- a **supervisor** that relaunches the conversion on failure (the 140V run used one; a PCIe link-down
  or driver reset costs one layer, not the run),
- the environment metadata + input checksums + output checksums captured as the evidence bundle.

Then load it in the pinned runtime (`exl3xpu`'s vLLM plugin, `quantization="exl3"`) and execute a

### D3. Quality (P3-12) on the same fixed corpus

- Held-out corpus: wikitext-2-raw-v1 **validation** split (the calibration used the *test* split) —
  tokenized once with the target tokenizer and reused verbatim.
- `scripts/evaluate_quality.py` (repo-side teacher-forced NLL/perplexity/KL, baseline vs quantized)
  and `scripts/evaluate_perplexity.py` (the same corpus inside the runtime).
- Compare against the 140V numbers: the *quality* must be identical (same weights, same recipe); only
  the *time* may differ.

### D4. Reproducibility (P3-14)

`scripts/repeat_layer_conversion.py` — repeat one layer through the identical code path and compare the
artifact byte-wise (sha256) with the published one. On the 140V this is a bit-for-bit expectation; the
same must hold per board, and the two boards must agree with each other.

**Gate D:** 32/32 layers published, P3-11 verification clean, runtime load + decode working, quality
numbers matching the 140V run.

## 7. Risks and mitigations (carried over from the 140V run)

| Risk | What we learned | Mitigation |
|---|---|---|
| **Memory starvation / pool squeeze** | On UMA, the host's page cache, `zram` and the desktop's GPU allocations starved the pool; 8 attempts were lost to `MemoryPressureError` | Dedicated VRAM removes the class of failure; still keep `MemAvailable` and `dev_free` visible in the logs |
| **Policy double counting** | The policy subtracted the live XPU allocation from a binding figure that *already* reflected it → zero admissible budget | Two documented knobs (`EXL3_MEMORY_RESERVE_GIB`, `EXL3_MEMORY_REFLECT_OUTSTANDING`); determine the regime per board (Phase B2) instead of copying the 140V values |
| **Per-layer allocation leak** | Each layer's decoded weights stayed alive through the next layer's quantization → +3.5 GiB/layer until the pool died | Fixed upstream (`0a9645b`); the per-layer `xpu_alloc` telemetry in the log is the regression guard |
| **Driver / PCIe resets** | `UR_RESULT_ERROR_DEVICE_LOST` (140V, under memory pressure) and "B70 PCIe links are unstable" (pinned runtime's log) | Supervisor + per-layer resume (one layer lost, not the run); baseline the PCIe error counters before the run and compare after |
| **CPU-side Cholesky fallback** | `ldlq.py:98` falls back to CPU on every layer → the host CPU may gate a fast GPU | Measure the CPU share in Phase C; if it dominates, it becomes a P2 item (XPU Cholesky) — do **not** change it mid-qualification |
| **Thermal / power throttling** | Sustained 15 h of encoder load | Log per-board clocks and temperature during the run (`xpu-smi`, `intel_gpu_top`); record them in the evidence (P3-10 asks for disclosed power/thermal conditions) |
| **Two boards in one machine** | PCIe slot/thermal contention could bias the comparison | Run the phases in a fixed order (B580 → B60), record slot/thermals, and idle the other board |
| **Silent divergence** | A board-specific kernel difference would silently change the weights | The P3-11 verification and the P3-14 byte-wise repeat are the guards; compare the artifacts against the 140V run (they must be identical for the same layer) |

## 10. Open questions to settle on the new machine

1. Does the driver expose a stable `max_single_alloc_bytes` (the single-allocation ceiling) on discrete VRAM?
2. Does the Level Zero runtime on the discrete board report `dev_free` that is **independent** of the
   host's page cache and `MemAvailable`? (Decides whether the watchdog and the reflected-counter
   regime are needed at all — expected: **no**.)
3. Is the encoder kernel bit-identical across SKUs (Xe-LG vs the 140V's Xe-LG), or does the discrete
   board's wider SIMD path change the search result? The encoder is *bit-exact by construction*; if
   the artifacts differ from the 140V run, that is a **bug**, not a board effect — investigate before
   comparing quality.
4. Does the CPU-side Cholesky fallback become the dominant cost on a 2–3× faster GPU? (Measure; if
   yes, raise it as a P2 item, do not patch it inside the qualification.)
5. Are both boards visible to the same vLLM/exl3xpu runtime simultaneously, and does the plugin's
   device selection need to be pinned (`XPU_VISIBLE_DEVICES` or similar) for the per-board runs?
